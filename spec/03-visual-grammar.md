# 03 — Визуальная грамматика

## 1. Базовая метафора: чертёж и материализация

Архитектура читается как два состояния одного и того же объекта:

```
M: голографический чертёж  →  фазовый сдвиг  →  R: работающий модуль
```

| Уровень UMLG | Образ | Что означает |
|---|---|---|
| система | поле чертежей / ансамбль модулей | вся модель |
| модуль/пакет | сектор | группа связанных типов |
| класс | стеклянная витрина с миниатюрой | тип, контракт, возможность |
| объект | монолит-модуль | экземпляр, факт, runtime |
| ресурс | стойка памяти | экземпляр ресурса, которым владеют |
| процесс | кольцо вокруг ядра | длящийся вычислительный процесс |
| стадия | направляющий канал | шаг конвейера |
| команда | гранёный сигнал | вызов или команда исполнения |
| актор | гироскопический пульт | контекст исполнения, не экземпляр |
| метод | порт/тракт на корпусе | операция над состоянием |
| атрибут | ячейка/слот | состояние |
| связь | линия/канал/луч | отношение |

Метафора нужна не для украшения, а чтобы пользователь мог **угадывать семантику до чтения подписей**. Если метафора врёт, она удаляется.

Ключевое правило: **M показывает форму будущего R-модуля, а не отдельный декоративный объект.** Переход M → R не заменяет силуэт, а «отвердевает» его: стекло становится металлом, контур — корпусом, миниатюра — самим элементом.

## 2. Класс: витрина чертежа

Класс — это **не** работающий модуль. Это проект, по которому можно собрать модуль.

Визуальные признаки:

- стеклянная витрина-параллелепипед с чётким контуром;
- материал прозрачный, почти без заливки; читается геометрия, а не поверхность;
- внутри стоит миниатюра формы R-двойника — обещание материализации;
- вывеска с именем типа;
- плинт витрины приглушён, чтобы не читаться как стол или постамент внутри сцены.

Почему не solid: solid означает «существует и работает». Если класс выглядит как работающий модуль, пользователь перестаёт различать тип и экземпляр — это главная ошибка, которую UMLG должен предотвращать.

### 2.1. Силуэты видов в референсном вьюере

Тип читается **формой**, а не цветом и не подписью. Цвет принадлежит миру (M — холодный, R — тёплый) и состоянию; силуэт должен работать в монохроме.

| Вид | Силуэт | Обязательные признаки |
|---|---|---|
| `class` | стеклянная витрина | полупрозрачный корпус, чёткий контур, внутри — миниатюра формы R-двойника |
| `abstractClass` | разомкнутый контур | отсутствует одно ребро, пунктир, бейдж `ghost`, макета нет |
| `interface` | шестиугольный порт | сквозное отверстие, два боковых разъёма, нет корпуса |
| `component` | платформа | низкий настил, угловые стойки, пунктирная граница, на настиле — миниатюры частей |
| `concept` | октаэдр | гранёный кристалл, внутренняя решётка, орбита |
| `object` | монолит-модуль | solid-корпус, утопленная верхняя панель, светящийся шов, передняя панель с линзой |
| `resource` | стойка памяти | стопка плит на угловых рейках, индикаторные полосы, крышка со слотом |
| `process` | кольцо вокруг ядра | вертикальное кольцо, гранёное ядро, свечение по ободу |
| `stage` | направляющий канал | труба, кольца-направляющие, стрелка потока, низкие пилоны |
| `command` | гранёный осколок | скошенный кристалл-носитель, воротник, светящийся наконечник |
| `actor` | гироскопический пульт | два скрещённых кольца вокруг небольшого ядра |

Правила:

1. **Силуэт важнее материала.** Класс и объект нельзя различать только прозрачностью.
2. **Размер не кодирует важность.** Все виды компактны; меньший размер — следствие узнаваемой формы, а не статуса.
3. **Один вид — один силуэт.** Нельзя переиспользовать силуэт витрины для ресурса, стадии или команды.
4. **Форма не зависит от `layout.json`.** Позиция и масштаб сцены — презентация; силуэт вида — грамматика.
5. **Макет внутри класса — обещание R-мира.** Если класс материализует сущность, внутри стоит миниатюра именно её силуэта по связи `materializes`. После фазового перехода форма не подменяется: тот же силуэт становится solid.
6. **Нет двойника — нет макета.** Класс без материализации показывает пустой пунктирный постамент. Отсутствие R-сущности нормально и не маскируется случайной формой.
7. **Компонент показывает свои части.** На настиле `component` стоят миниатюры форм того, что он содержит или развёртывает; это связывает сектор с его линией.
8. **M-превью — это почти wireframe.** Поверхности превью едва заметны; читаются контур и акценты. Иначе миниатюра превращается в самостоятельный объект внутри витрины.

## 3. Объект: работающий модуль

Объект:

- solid-геометрия, материал, вес;
- корпус с утопленной верхней панелью и светящимся швом;
- передняя сервисная панель, линза датчика, вентиляционные рёбра;
- имя вида `Circle#2`.

Один класс может дать много объектов. Они не обязаны стоять рядом, но layout по умолчанию старается держать их в зоне видимости класса — для пространственной памяти.

Силуэт объекта совпадает с макетом внутри класса, который его материализует: переход M → R не заменяет форму, а кристаллизует её. То же правило действует для ресурса, процесса, стадии и команды.

### 3.1. Ресурс: стойка памяти

`resource` — не модуль общего назначения. Это ёмкость, буфер или хранилище, которое подключено к потребителям и имеет собственное состояние: заполненность, валидность, версию.

- solid-корпус, но без собственных сервисных панелей и операторов;
- стопка плит на угловых рейках читается как память, а не как здание;
- состояние читается по индикаторным полосам, а не по цвету типа;
- входы и выходы отмечены портами;
- связи `binding` идут от потребителя к ресурсу.

Ресурс — экземпляр, поэтому он может иметь провенанс и `drift`. Он не притворяется объектом: если для ресурса нужна геометрия монолита, это ошибка грамматики.

### 3.2. Процесс: кольцо вокруг ядра

`process` — длящееся вычисление или конвейерная обработка, у которой есть вход, выход и собственное состояние.

- вертикальное кольцо вокруг гранёного ядра;
- ядро вращается медленнее, чем кольцо, или наоборот — но только если это следует из модели;
- нет корпуса-монолита и нет сервисной панели;
- активность показывается свечением обода, а не «важностью».

### 3.3. Стадия: направляющий канал

`stage` — отрезок конвейера между модулями. У стадии один входной поток и один выходной, а порядок задаётся связями `flow`.

- труба/жёлоб с кольцами-направляющими и стрелкой, а не корпус;
- имя стадии на табличке у входа;
- активная стадия подсвечивается движением потока, а не «важностью»;
- у стадии нет стен, ячеек памяти и собственного пульта.

### 3.4. Команда: гранёный сигнал

`command` — сигнал, тикет или вызов, который движется по линии и несёт параметры.

- компактный гранёный носитель, приподнятый над маленькой площадкой;
- воротник и светящийся наконечник показывают направление;
- появляется в точке диспетчеризации и исчезает после исполнения;
- имеет владельца-актора и цель-стадию;
- не является модулем и не имеет постоянного места в пространстве.

### 3.5. Актёр: гироскопический пульт

`actor` — контекст исполнения (CPU, GPU, поток, процесс-хост), а не экземпляр класса.

- два скрещённых кольца вокруг небольшого ядра;
- кольца читаются как система координат/гироскоп, а не как устройство;
- не материализуется и не имеет провенанса;
- может быть источником `call`/`signal` и `observes`;
- его нельзя рисовать как объект или ресурс.

Правило: **object, resource, process, stage, command и actor различаются геометрией, а не только подписью.** Общая «корпусная» геометрия для всех R-сущностей запрещена.

## 4. Абстрактный класс: призрак

### 4.1 Определение

> Абстрактный класс — сущность M-мира, которая не может быть материализована напрямую и не имеет runtime-прошлого.

Это точнее, чем «мёртвый» или «нереализованный».

### 4.2 Визуал

- та же витрина и то же место, что у обычного класса, но с обязательным разрывом контура;
- холодный полупрозрачный материал;
- отсутствие макета внутри;
- имя курсивом + бейдж `{abstract}` + иконка призрака;
- вход заблокирован: «прямое создание невозможно»;
- NPC — голографический куратор, объясняющий контракт.

Обязательный геометрический признак: **контур разомкнут** (несомкнутая витрина, пунктир). Он должен читаться без цвета, прозрачности и подписи — иначе `abstract` визуально сливается с обычным классом и состояниями из таблицы ниже.

### 4.3 Чего призрак **не** означает

| Не означает | Как отличить |
|---|---|
| `deprecated` | потускневший контур, предупреждающая лента, бейдж `deprecated` |
| `unused` | приглушённый, но solid; бейдж `unused` |
| `deleted` | руины/обломки, нет контура |
| `mock/stub` | яркий голограммный манекен, бейдж `mock` |
| `remote/proxy` | зеркало/док, бейдж `proxy` |
| `sealed/final` | запертый порт, бейдж `sealed` |

Один и тот же полупрозрачный вид не может означать пять разных вещей. Это правило важнее красоты.

### 4.4 Призрачность члена ≠ призрачность класса

| Что | Визуал | Смысл |
|---|---|---|
| абстрактный класс | разомкнутая витрина | нельзя создать напрямую |
| абстрактный метод | пустой пунктирный порт | реализации нет |
| конкретный метод в абстрактном классе | призрачный, но рабочий порт | реализация есть, наследуется |
| атрибут абстрактного класса | призрачная ячейка с меткой `inherited` | состояние живёт в подклассах |
| конструктор | призрачный пусковой тракт | вызывается только через подкласс |
| статический член | solid общая ячейка вне витрины | реален и общий |

Правило: **абстрактный класс — призрачный, но не обязательно пустой.**

### 4.5 Материализация призрака

Попытка создать экземпляр абстрактного класса:

1. открывает «порт материализации»;
2. показывает список конкретных подклассов;
3. объясняет, какой контракт каждый выполняет;
4. после выбора создаёт объект подкласса;
5. подсвечивает линию наследования как «луч материализации».

Это не ошибка, а обучающий момент.

## 5. Интерфейс: контрактный порт

Интерфейс — не витрина. Это:

- парящий шестиугольный порт;
- сертификат/разъём;
- набор обязательств без тела и состояния.

Визуал:

- нет корпуса и слотов;
- есть только порты/разъёмы с сигнатурами;
- соединяется с классами линией реализации (пунктир + треугольник);
- бейдж `{interface}`.

Почему не призрак: призрак — это «витрина, которую нельзя материализовать». Интерфейс — это «стандарт, которому можно соответствовать». Разные онтологии, разный визуал.

## 6. Члены класса

Члены читаются как внутреннее устройство модуля: слоты, тракты и датчики на корпусе, а не как отдельная мини-сцена.

### 6.1 Атрибут

- ячейка/слот в корпусе;
- имя и тип на табличке;
- видимость: замок (private), ключ-карта (protected), открытый слот (public);
- `static` — общая ячейка вне витрины;
- `const`/`readonly` — опечатанная ячейка;
- `optional` — пустой слот с пунктиром.

### 6.2 Метод

- порт/тракт на корпусе;
- табличка с именем и сигнатурой;
- параметры — входной канал с ячейками;
- возврат — выходной канал;
- `abstract` — пустой пунктирный порт;
- `static` — съёмный инструмент;
- `async` — тракт с буфером ожидания.

### 6.3 Свойство (getter/setter)

- датчик/клапан;
- показывает значение;
- `readonly` — только датчик, без клапана.

### 6.4 Событие/сигнал

- маяк/лампа;
- мигает при срабатывании (не чаще 3 Гц);
- не является методом: у него нет входного тракта.

### 6.5 Исключение

- аварийный порт;
- красная сигнализация;
- путь эвакуации к обработчику.

### 6.6 Инвариант

- маркер правил на корпусе;
- при нарушении краснеет и вызывает инспектора;
- не является исполняемым элементом.

## 7. Связи

| UML | Визуал | Направление | Подпись |
|---|---|---|---|
| наследование | луч материализации снизу вверх | подкласс → суперкласс | `extends` |
| реализация | пунктир к контрактному порту | класс → интерфейс | `implements` |
| композиция | части внутри модуля, жёсткая связь | целое → часть | ромб + кратность |
| агрегация | съёмный модуль, общая связь | целое → часть | пустой ромб |
| ассоциация | линия/канал | любой | роль + кратность |
| зависимость | временная поставка, пунктир | зависимый → зависимость | `uses` |
| поток | полоса движения | источник → сток | объём/частота |
| вызов | курьер/сигнал | вызывающий → вызываемый | сигнатура |
| сигнал | маяк | источник → слушатели | имя события |
| привязка | кабель/док | потребитель → ресурс | слот/индекс |

Правила:

1. **Положение не создаёт связь.** Линия обязательна.
2. **Кратность — текст, не толщина.** Толщина может кодировать поток, но не `1..*`.
3. **Роль — текст у конца линии.**
4. **Цвет линии — только состояние** (`drift`, `deprecated`, `active`).
5. **Пересечения минимизируются**, но не любой ценой: лучше честная линия, чем ложная группировка.

## 8. NPC

NPC — семантические агенты. Их поведение генерируется из модели, а не рисуется вручную.

| NPC | Отвечает за | Пример действия |
|---|---|---|
| Куратор | класс | объясняет назначение, инварианты, жизненный цикл |
| Оператор | метод | берёт параметры, запускает тракт, выдаёт результат |
| Курьер | связь/вызов | движется между модулями; частота = частота вызовов |
| Инспектор | формальные данные | по запросу показывает сигнатуру, тип, кратность |
| Охранник | видимость/доступ | блокирует приватное |
| Диспетчер | полиморфизм | выбирает реализацию |
| Техник по безопасности | исключения/инварианты | реагирует на нарушения |

Призрак — не отдельная роль NPC. Абстрактный класс обслуживает **Куратор**: он объясняет контракт и запрет прямой материализации. Вводить «NPC-призрака» нельзя, иначе роли начнут дублировать друг друга.

Жёсткие правила:

1. **NPC не заменяют формальные данные.** Точная сигнатура всегда доступна в инспекторе.
2. **NPC не кодируют тип, кратность и видимость.** Это делают геометрия и текст.
3. **Поведение NPC выводится из модели.** Если для каждого метода нужен свой аниматор, проект не масштабируется.
4. **NPC можно отключить.** Architecture mode работает без них.

## 9. Режимы чтения

| Режим | NPC | Подписи | Анимация | Для кого |
|---|---|---|---|---|
| `story` | включены | минимальные | есть | новички, обучение |
| `architecture` | приглушены/выключены | полные | минимум | ревью, проектирование |
| `debug` | агенты runtime | метрики | живая | отладка |
| `presentation` | по сценарию | крупные | кинематографичная | демонстрация |

Плотность семантики — ползунок от «только имена» до «полная карточка». Это ответ на «понятно всем»: новичок начинает со `story`, архитектор сразу включает `architecture`.

## 10. Визуальные переменные

Разрешённые каналы и их значения:

| Канал | Допустимые значения | Запрещено |
|---|---|---|
| материал | ghost / glass / solid / rust / clearcoat | произвольные текстуры без смысла |
| прозрачность | уровень существования (0.2–0.6 ghost) | декор |
| цвет | мир (M холодный / R тёплый) и состояние (normal/deprecated/drift/error) | кодирование типа |
| контур | чёткий / пунктир / отсутствует | случайный |
| движение | поток, вызов, сигнал | декоративная анимация |
| звук | мир, переход, авария | фоновая музыка как семантика |
| размер | фиксирован по уровню | «важность» |
| положение | группировка/вложенность | «важность» |

Правило: **если канал не описан в этой таблице, он не кодирует семантику.**

## 11. LOD (уровни детализации)

| Уровень | Что видно | Когда |
|---|---|---|
| L0 | сектор/ансамбль, только имена | обзор |
| L1 | модули, ключевые связи | навигация |
| L2 | члены класса, подписи | работа |
| L3 | сигнатуры, типы, кратности, инварианты | ревью |
| L4 | история, метрики, провенанс | отладка |

Правила:

- переход между LOD плавный и обратимо;
- LOD не меняет семантику, только детализацию;
- на L0 связи не исчезают бесследно: остаются агрегированные пучки;
- агрегация сохраняет вид связи: разные `kind` не сливаются в один безымянный пучок;
- `drift` не агрегируется и не исчезает: он остаётся отдельным маркером на любом LOD;
- LOD по умолчанию зависит от расстояния и режима чтения.

## 12. Масштабирование

| Количество | Представление |
|---|---|
| 1 объект | отдельный модуль |
| 2–20 | отдельные модули |
| 20–1000 | секторы/ряды, агрегированные |
| > 1000 | облако/толпа, статистика |

Один объект = один экземпляр. Тысяча = облако, а не тысяча NPC.

При агрегации 20+ сущностей группировка идёт по `kind` и состоянию. `drift` выносится в отдельный слой и не растворяется в статистике.

## 13. Где метафора ломается

Эти случаи должны быть спроектированы явно:

| Случай | Решение |
|---|---|
| Generic-класс | витрина с контейнерами `T` |
| Вложенный класс | витрина внутри витрины, отдельный вход |
| Singleton | единственная витрина с одним ключом |
| Enum | набор маркированных ячеек |
| Лямбда | переносной тракт |
| Record/struct | небольшой поддон, не витрина |
| Модуль/пакет | сектор |
| Функция без класса | отдельный тракт на площади |
| Макрос/декоратор | наклейка/модификатор на корпусе |
| Множественное наследование | несколько лучей материализации, конфликт подсвечивается |

Если случай не покрыт, он не «выкручивается» визуально на месте, а добавляется в спецификацию.

## 14. Проверка грамматики

Минимальный тест:

1. Пользователь находит метод за 10 секунд.
2. Пользователь отличает класс от объекта без подсказки.
3. Пользователь объясняет, почему у призрака нет экземпляров.
4. Пользователь различает `abstract` и `deprecated`.
5. Пользователь читает кратность связи.
6. Пользователь узнаёт ресурс, стадию и команду по силуэту до чтения подписи.

Если хотя бы один пункт провален — правится грамматика, а не пользователь.
