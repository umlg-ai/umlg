# 01 — Миры M и R

## 1. Зачем миры

UML смешивает в одной диаграмме то, что *спроектировано*, и то, что *существует*. Из-за этого:

- абстрактный класс выглядит как обычный, но с курсивом;
- объект на диаграмме классов неотличим от класса визуально;
- runtime-состояние живёт в отдельном документе;
- расхождение модели и реальности не видно.

UMLG разводит это по **онтологиям**. Мир — не слой и не тема оформления. Мир — это набор правил о том, что в нём может существовать.

## 2. M-мир: Замысел

**Вопрос:** что *может* существовать и на каких условиях?

Содержит:

- классы (`class`);
- абстрактные классы (`abstractClass`);
- интерфейсы (`interface`);
- компоненты и модули (`component`);
- концепты и решения (`concept`);
- сигнатуры методов, атрибуты, инварианты;
- связи: наследование, реализация, композиция, агрегация, зависимость, ассоциация.

Свойства M-мира:

| Свойство | Правило |
|---|---|
| Время | design-time; версии и изменения, но не runtime-история |
| Материал | голограмма, чертёж, холодный свет |
| Вход | у абстрактного класса вход заблокирован |
| NPC | инструкторы, архитекторы, инспекторы контрактов |
| Действия | проектирование, ревью, сравнение, материализация |

M-мир — источник истины о **структуре и контрактах**.

## 3. R-мир: Воплощение

**Вопрос:** что *существует сейчас* и в каком состоянии?

Содержит:

- объекты и экземпляры (`object`);
- ресурсы (`resource`): буферы, текстуры, framebuffer;
- процессы и стадии (`process`, `stage`);
- команды и вызовы (`command`);
- акторов (`actor`): CPU, GPU, поток, сервис;
- runtime-состояние, метрики, ошибки;
- связи: flow, call, signal, binding.

Свойства R-мира:

| Свойство | Правило |
|---|---|
| Время | runtime; реальное или симулированное |
| Материал | solid, вес, тени, тёплый свет |
| Вход | доступен, если объект жив |
| NPC | операторы, курьеры, рабочие, диспетчеры |
| Действия | наблюдение, отладка, инспекция, сравнение с контрактом |

R-мир — источник истины о **фактическом состоянии**.

## 4. Чего в каком мире нет

| Понятие | M | R | Комментарий |
|---|---|---|---|
| Класс | есть | нет | в R есть только экземпляры и их класс как метаданные |
| Объект | нет | есть | в M объект может быть показан только как «эхо»/счётчик, не как тело |
| Абстрактный класс | есть (призрак) | **нет** | нет материального воплощения |
| Абстрактный метод | есть (пустой слот) | нет | пока подкласс не дал реализацию |
| Метрика | нет | есть | в M — только как ожидание/бюджет |
| Инвариант | есть | проявляется как нарушение | в R инвариант виден через аварию |
| Код | нет в v0.1 | нет в v0.1 | зарезервирован S-мир |

## 5. Связи между мирами

Связи — first-class. Они не «линии для красоты», а утверждения о соответствии.

| Вид | Из (M) | В (R) | Смысл | Кардинальность |
|---|---|---|---|---|
| `materializes` | класс | объект | экземпляр создан по типу | 1 : 0..* |
| `implements` | интерфейс | класс (M) | класс выполняет контракт | 1 : 0..* |
| `deploys` | компонент | процесс/узел | развёртывание | 1 : 0..* |
| `observes` | runtime-факт | модель | метрика подтверждает/опровергает | * : 1 |
| `drift` | модель | runtime | расхождение | 1 : 0..* |

Правила:

1. `materializes` идёт только от **конкретного** класса. Абстрактный класс не может быть источником.
2. Один объект имеет ровно один материализующий класс. Если классов несколько — это ошибка модели (или явный множественный тип, который v0.1 не поддерживает).
3. `implements` живёт внутри M-мира и не пересекает границу.
4. `observes` не меняет модель. Наблюдение — это факт, а не правка.
5. `drift` — диагностический маркер, а не связь владения.

## 6. Материализация

Материализация — не «переход в другой мир», а **создание сущности в R по типу из M**.

```
M:  Circle (class)
        │ materializes
        ▼
R:  Circle#1   Circle#2
```

Правила:

- у конкретного класса может быть 0, 1 или много объектов;
- абстрактный класс требует выбора подкласса;
- объект без класса — сирота (`drift`), а не «нормальный объект»;
- объект не наследует координаты класса автоматически, но layout по умолчанию старается сохранять пространственную память.

## 7. Источник истины

Это ключевое правило, которое предотвращает бесконечные споры «кто главнее».

| Аспект | Источник истины |
|---|---|
| Наличие типа | M |
| Сигнатура метода | M |
| Инвариант | M |
| Наличие экземпляра | R |
| Состояние экземпляра | R |
| Метрика | R |
| Соответствие «объект ↔ класс» | связь `materializes` |
| Расхождение | `drift` + правило валидации |

Следствие: **нельзя «исправить» R, переписав M**, если речь о фактическом состоянии. И нельзя объявить тип существующим, потому что «в проде что-то работает»: это drift, а не тип.

## 8. Drift

Drift — это не ошибка рендера. Это обнаруженное расхождение.

Виды:

| Вид | Пример | Отображение |
|---|---|---|
| `orphan-object` | объект есть, класса нет | красная нить к пустому месту, бейдж `drift: class missing` |
| `unmaterialized` | класс есть, объектов нет | нормально, не drift |
| `signature-mismatch` | объект ведёт себя не по контракту | связь `observe` краснеет |
| `deprecated-instance` | класс помечен `deprecated`, объекты живы | ржавая рамка + бейдж |
| `abstract-instantiated` | у абстрактного класса есть объект | **ошибка модели**, блокирует валидацию |

Правила:

1. Drift никогда не скрывается автоматически.
2. Drift не «лечится» удалением объекта без решения пользователя.
3. Drift доступен как список — это часть модели, а не только визуальный эффект.

## 9. Присутствие

Определения:

- **Присутствие** — где пользователь может действовать.
- **Наблюдение** — что пользователь может узнать о другом мире.

Правило v0.1:

> Присутствие ровно одно. Наблюдение другого мира ограничено метаданными о выбранном двойнике.

Что это значит практически:

- нельзя редактировать M, стоя в R;
- нельзя «подсмотреть» сцену R из M;
- можно узнать: «у `Circle` два экземпляра», «выбранный двойник — `Circle#2`», «у `Shape` нет материального воплощения»;
- переход — единственный способ сменить присутствие.

## 10. Почему не три мира в v0.1

S-мир (код, шейдеры, конфиги) — соблазнителен, но:

- добавляет третий уровень сложности;
- требует решить, является ли код «инструкцией» или «артефактом»;
- удваивает работу над viewer.

Решение: зарезервировать `world: "S"` в схеме как будущее расширение, но не использовать в v0.1. Правило «одно присутствие» должно выдержать добавление миров без переделки.

## 11. Инварианты мира (проверяемые)

1. `abstractClass` не может быть источником `materializes`.
2. `object` не может быть источником `inheritance`.
3. `interface` не может иметь `materializes` напрямую к объекту.
4. Каждый `object` имеет ровно один `materializes` (или явный `drift`).
5. Каждая связь ссылается на существующие `id`.
6. Элемент принадлежит ровно одному миру (`world` — обязательное поле).
7. `layout` не содержит семантических полей.
