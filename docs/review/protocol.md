# Review Protocol

## 1. Принцип

Рецензенты работают **независимо и адверсариально**. Цель — не консенсус, а полный список проблем. Синтез делает отдельный шаг, после сбора отчётов.

## 2. Вход

Рецензент получает:

- путь к репозиторию;
- роль и промпт;
- тип изменения (diff, PR, раздел, пример);
- ограничение по времени и объёму.

Рецензент **не получает**:

- выводы других рецензентов;
- защиту автора;
- «правильный» ответ.

## 3. Что проверять

1. **Соответствие спецификации.** Не только «нет ли ошибки», но и «не противоречит ли изменение другим разделам».
2. **Доказательства.** Ссылка на файл и раздел обязательна.
3. **Проверяемость.** Можно ли это проверить валидатором, тестом или вопросом self-check?
4. **Масштабируемость.** Что сломается на 50 классах, 1000 объектах, трёх мирах?
5. **Альтернативы.** Есть ли более простая модель?

## 4. Severity

- **P0** — противоречие онтологии, невалидный JSON, невозможность материализации, утечка другого мира.
- **P1** — ложная метафора, неверная предметная область, непроходимый self-check, нарушение доступности.
- **P2** — неполнота, двусмысленность, отсутствие примера.
- **P3** — стиль, оформление, вкус.

## 5. Verdict

| Verdict | Когда |
|---|---|
| `accept` | нет P0/P1, P2 заведены в issues |
| `accept with changes` | есть P1, но они исправимы в этом PR |
| `reject` | есть P0 или изменение ухудшает онтологию |
| `defer` | не хватает данных/примеров |

## 6. Синтез

1. Собрать findings, убрать дубли.
2. Повысить severity, если находка подтверждена двумя ролями.
3. Разделить: «блокирует», «issue», «отклонено».
4. Записать в `docs/review/YYYY-MM-DD-<topic>.md`.
5. P0/P1 → issue или PR.
6. Если решение меняет онтологию — `docs/decisions/NNNN-*.md`.

## 7. Конфликт ролей

Если доменный эксперт и онтолог спорят:

- онтолог решает, **что означает**;
- доменный эксперт решает, **как это устроено**;
- если конфликт не решается — это RFC, а не голосование.

## 8. Ограничение по времени

| Тип | Время на роль |
|---|---:|
| diff | 10 мин |
| пример/тема | 20 мин |
| схема/viewpoint | 30 мин |
| ядро/метафора | 45 мин |

Рецензент, не уложившийся, пишет `defer` и список открытых вопросов.

## 9. Запрещено

- Хвалить без конкретики.
- Предлагать «переписать всё» без миграции.
- Менять файлы во время review.
- Скрывать неуверенность: `confidence` обязателен.
- Соглашаться с автором из вежливости.

## 10. Метрика качества ревью

Хорошее ревью:

- находит хотя бы один P1/P2 в 50% случаев;
- не содержит findings без evidence;
- различает «ошибка» и «вкус»;
- предлагает проверяемое исправление.
